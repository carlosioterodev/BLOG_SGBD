PostgreSQL en acción: ejemplo de uso

En las entradas anteriores hablamos de teoría: qué es un SGBD, cómo se clasifican y cómo funciona por dentro PostgreSQL. Esta vez toca escribir SQL. Vamos a montar, en cinco pasos, la base de datos del propio blog: crear la base, definir tablas con claves y un campo jsonb, cargar datos reales, consultarlos con JOIN y terminar con seguridad y respaldo. Todo el código se puede copiar y pegar tal cual en una terminal.

Requisitos

Antes de empezar hacen falta dos cosas. Primera: tener PostgreSQL 18 instalado; la descarga y la documentación oficial están en la web del proyecto (postgresql.org/docs). Segunda: abrir una terminal y conectarse con psql, el cliente de línea de comandos que viene con el servidor. Si psql --version responde, estamos listos; si el servidor no está corriendo, hay que iniciarlo antes de continuar.

Idea clave

Un SGBD se usa desde un cliente (psql, un editor SQL, una aplicación web) que se conecta al servidor. Todo lo que escribimos viaja en SQL; el servidor es quien lo analiza, lo planifica y lo ejecuta sobre el disco.

El esquema paso a paso

Paso 1 — crear la base de datos y conectarse

Creamos la base y entramos a ella. El primer comando es SQL; el segundo es una meta-instrucción de psql (empieza con barra invertida) que reconecta la sesión recién creada: 

-- Paso 1: crear la base y conectarse
CREATE DATABASE blog_sgbd;
\c blog_sgbd

Paso 2 — crear las tablas

Definimos dos tablas. Fíjate en cada cláusula: PRIMARY KEY marca la clave primaria que identifica de forma única cada fila; NOT NULL impide guardar valores vacíos en esa columna; REFERENCES crea la clave foránea que obliga a que autor_id exista en autores; y jsonb es un tipo binario para documentos JSON que se puede consultar con índices. serial genera un identificador incremental en cada inserción: 

-- Paso 2: tablas con claves y JSONB
CREATE TABLE autores (
  id serial PRIMARY KEY,
  nombre varchar(80) NOT NULL,
  iniciales char(2)
);

CREATE TABLE entradas (
  id serial PRIMARY KEY,
  titulo varchar(120) NOT NULL,
  fecha date NOT NULL,
  minutos int NOT NULL,
  autor_id int NOT NULL REFERENCES autores(id),
  tags jsonb NOT NULL
);

Paso 3 — cargar los datos

Insertamos cuatro autores y cuatro entradas. En tags usamos la notación '[...]'::jsonb, que convierte una cadena en JSON binario listo para consultar: 

-- Paso 3: datos de prueba
INSERT INTO autores (nombre, iniciales) VALUES
  ('Aaron Pérez', 'AP'),
  ('Carlos Otero', 'CO'),
  ('Enrique López', 'EL'),
  ('Cristian Carrera', 'CC');

INSERT INTO entradas (titulo, fecha, minutos, autor_id, tags) VALUES
  ('¿Qué es un SGBD?', '2026-11-14', 5, 1, '["conceptos","sql"]'::jsonb),
  ('Clasificación de los SGBD', '2026-11-15', 6, 2, '["conceptos","modelos"]'::jsonb),
  ('PostgreSQL: características', '2026-11-16', 6, 3, '["postgresql","sql"]'::jsonb),
  ('PostgreSQL: estructura interna', '2026-11-16', 6, 3, '["postgresql","administracion"]'::jsonb);

Consultas con JOIN y JSONB

Con los datos cargados llega lo interesante. Cuatro consultas típicas de cualquier proyecto:

  • (a) JOIN + ORDER BY: une entradas con autores por la clave foránea y lista los artículos con el nombre de quien los escribió.
  • (b) Contención en JSONB: el operador @> pregunta «¿este arreglo contiene la etiqueta?».
  • (c) Índice GIN: acelera justo esa búsqueda dentro del JSON.
  • (d) COUNT + GROUP BY: cuenta cuántas entradas tiene cada autor.
-- (a) entradas con el nombre del autor
SELECT e.titulo, e.fecha, a.nombre
FROM entradas AS e
JOIN autores AS a ON a.id = e.autor_id
ORDER BY e.fecha DESC;

-- (b) buscar por etiqueta en JSONB (contención)
SELECT titulo
FROM entradas
WHERE tags @> '["postgresql"]'::jsonb;

-- (c) índice GIN: imprescindible para que (b) no lea todas las filas
CREATE INDEX idx_entradas_tags
ON entradas USING gin (tags);

-- (d) entradas por autor
SELECT a.nombre, COUNT(*) AS entradas
FROM autores AS a
JOIN entradas AS e ON e.autor_id = a.id
GROUP BY a.nombre
ORDER BY entradas DESC;

¿Por qué un índice GIN (Generalized Inverted Index)? Porque está pensado para valores compuestos: descompone el JSONB en todas las etiquetas que contiene y permite localizarlas sin recorrer la tabla entera. Un índice ordinario no sirve aquí, ya que compara valores completos y tags es una estructura anidada.

Seguridad y respaldo

Un sistema real nunca se usa solo desde el superusuario. Creamos un rol con acceso de lectura y le damos permiso únicamente sobre lo que debe ver; después, exportamos la base completa con pg_dump para poder restaurarla ante cualquier fallo: 

-- crear un usuario de solo lectura
CREATE ROLE lector LOGIN PASSWORD 'UACI2026';
GRANT SELECT ON entradas TO lector;

-- respaldo de la base completa (desde la terminal)
pg_dump -U postgres blog_sgbd > respaldo.sql

Con esto cerramos el ciclo completo de administración que vimos en la teoría: definición (DDL), manipulación (DML), control (permisos) y administración (respaldo).

Ideas para llevar

Resumen

1) Un proyecto se levanta en cinco pasos: crear la base, definir el esquema con claves primarias, foráneas y restricciones NOT NULL, cargar datos, consultar y respaldar. 2) El JOIN une lo que guardamos en tablas distintas y el jsonb flexibiliza lo que aún no tiene forma fija. 3) Índices GIN, permisos con GRANT y pg_dump son la diferencia entre una demo y un sistema en producción.

Así cerramos el recorrido completo de la materia: partimos del DMER y de la teoría del SGBD, clasificamos los modelos, abrimos el motor de PostgreSQL y terminamos escribiendo SQL real. De la teoría a la práctica, en cuatro pasos y una terminal.
