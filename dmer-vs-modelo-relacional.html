DMER vs. Diagrama Modelo Relacional

El Proyecto Final pide dos diagramas y conviene no confundirlos: el DMER (Diagrama Modelo Entidad-Relación) y el Diagrama Modelo Relacional. Aunque describen el mismo diseño, se dibujan en momentos distintos.

El DMER llega primero, cuando aún no pensamos en tablas; el relacional, después, cuando hay que traducir el diseño a algo que el SGBD pueda ejecutar.

El DMER (Chen, 1976)

El Diagrama Modelo Entidad-Relación fue propuesto por Peter Chen en 1976 y se dibuja con una notación geométrica fija: rectángulo para entidad, rombo para relación, elipse para atributo y rectángulo doble para entidad débil. Describe cuatro cosas:

  • Entidades: objetos del mundo real que guardamos (CLIENTE, PRODUCTO). Una entidad fuerte tiene clave propia; una débil solo existe en función de otra y se representa con el rectángulo doble.
  • Atributos: características de la entidad. Hay simples (id_cli), compuestos (nombre y apellido), de clave (subrayados: identifican al registro) y derivados (calculados, como la edad a partir de la fecha de nacimiento).
  • Relaciones: asociaciones entre entidades, dibujadas como rombo. Según cuántas instancias participen, son 1:1, 1:N o N:M.
  • Cardinalidad y participación: la cardinalidad indica cuántas instancias intervienen; la participación puede ser total (todas participan) u opcional (solo algunas).
Idea clave

El DMER es un diagrama conceptual/lógico: dice qué datos existen y cómo se relacionan, pero no depende del SGBD: puede dibujarse en una pizarra antes de elegir el motor.

El Diagrama Modelo Relacional

El Diagrama Modelo Relacional traduce ese diseño al lenguaje de tablas: ya no hay rombos ni elipses, sino tablas con nombre, columnas con tipo de dato, la clave primaria (PK) destacada y claves foráneas (FK) que apuntan a la PK de otra tabla.

  • Cada entidad se dibuja como una tabla y cada atributo como una columna con su tipo (INTEGER, VARCHAR, DATE, NUMERIC).
  • La PK identifica de forma única cada fila; la FK materializa en columna lo que en el DMER era un rombo.
  • Por eso el diagrama es directamente implementable con CREATE TABLE: aquí sí importa el SGBD, porque tipos y restricciones dependen del motor.

Reglas de transformación DMER → Relacional

Pasar de un diagrama a otro no es improvisar: son reglas establecidas que se aplican en este orden:

  1. Cada entidad → una tabla con el mismo nombre.
  2. Cada atributo → una columna, conservando el tipo de dato que corresponda.
  3. Una relación N:M → una tabla intermedia cuya clave primaria está formada por las PK de las dos entidades.
  4. Una relación 1:N → una FK en el lado N (el lado «muchos»), para no duplicar columnas.
  5. Una relación 1:1 → la FK en el lado más fuerte, o la fusión de ambas tablas si comparten la misma clave.
  6. Una entidad débil → una tabla con PK compuesta que referencia a la entidad fuerte de la que depende.

Ejemplo narrado con SQL

Retomemos la figura. CLIENTE y PRODUCTO son entidades fuertes: cada una se vuelve una tabla con su propia PK (id_cli y id_prod). El rombo COMPRA es una relación N:M: un cliente compra muchos productos y un producto puede ser comprado por muchos clientes.

Por la regla N:M nace una tercera tabla, COMPRA, con PK compuesta (id_cli, id_prod) y dos claves foráneas que apuntan a las tablas madre. El atributo fecha, que en el DMER colgaba de la relación, se convierte en una columna más de esa tabla intermedia. El resultado es directamente ejecutable: 

-- Resultado de la transformación del diagrama
CREATE TABLE cliente (
  id_cli  INTEGER PRIMARY KEY,
  nombre  VARCHAR(80) NOT NULL
);

CREATE TABLE producto (
  id_prod INTEGER PRIMARY KEY,
  precio  NUMERIC(10,2) NOT NULL
);

CREATE TABLE compra (
  id_cli  INTEGER NOT NULL,
  id_prod INTEGER NOT NULL,
  fecha   DATE NOT NULL,
  PRIMARY KEY (id_cli, id_prod),
  FOREIGN KEY (id_cli)  REFERENCES cliente(id_cli),
  FOREIGN KEY (id_prod) REFERENCES producto(id_prod)
);

Cada regla quedó reflejada en el esquema: dos tablas por las entidades, una intermedia por la relación N:M, la PK compuesta que identifica a COMPRA y las FK que sustituyen al rombo.

Ideas para llevar

Resumen

1) El DMER modela el «qué» y no depende del SGBD; el modelo relacional modela el «cómo» y sí depende del motor. 2) La transformación sigue reglas fijas: entidad → tabla, N:M → tabla intermedia, 1:N → FK en el lado N, entidad débil → PK compuesta. 3) Sin esas reglas, un diagrama bien dibujado no se convierte en un esquema que funcione.

Con el diseño traducido a tablas, toca elegir el motor que lo materialice: PostgreSQL, tema de la siguiente entrada.
