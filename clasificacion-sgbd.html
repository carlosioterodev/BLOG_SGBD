Clasificación de los SGBD

CC Cristian Carrera 14 de noviembre de 2026 6 min de lectura

La rúbrica del proyecto pide clasificar los SGBD según la necesidad del proyecto, no según la popularidad de cada marca. Para eso manejamos tres criterios, cada uno con su propia pregunta: ¿cuántas personas usarán la base a la vez?, ¿con qué estructura se organiza la información? y ¿cómo se reparte esa información entre equipos y sedes? Ningún criterio es superior a los otros: sirven para descartar rápido las opciones que no encajan con el problema que vamos a resolver.

Criterio 1 — Cantidad de usuarios

El primer criterio mira cuántos usuarios o aplicaciones pueden leer y escribir al mismo tiempo sin estorbarse. De ahí salen dos grandes familias:

  • Monousuario: admite un solo usuario a la vez; si otro intenta abrir la base, espera o recibe un aviso. Es el caso de SQLite en modo single-user y de Microsoft Access. Conviene para herramientas personales, prototipos o archivos que trabaja una sola persona.
  • Multiusuario: acepta muchas conexiones simultáneas y las coordina con bloqueos y control de concurrencia para que las escrituras no se pisen. Aquí están PostgreSQL, Oracle y SQL Server: es el escenario normal de un sistema web o de una oficina completa.

Como subtipo dentro de este criterio conviene distinguir la arquitectura cliente-servidor, donde la aplicación corre en el cliente y la base de datos vive en un servidor al que se conecta por red, de la embebida, donde el motor de la base corre dentro de la misma aplicación. SQLite y Access son embebidos; un PostgreSQL instalado en un servidor es cliente-servidor. El mismo producto puede usarse embebido en desarrollo y cliente-servidor en producción.

Criterio 2 — Modelo de datos

El segundo criterio describe cómo se organizan los datos por dentro y, en consecuencia, qué lenguaje usaremos para consultarlos:

Modelo Cómo organiza los datos Ejemplos Cuándo conviene
Relacional Tablas con filas y columnas, unidas por claves; se consulta con SQL. PostgreSQL, MySQL, SQL Server, Oracle Datos con reglas estrictas, reportes y consultas con JOIN.
Jerárquico Árbol padre-hijo: cada registro tiene un único padre. IBM IMS Estructuras estables y navegación de arriba hacia abajo.
En red Árbol generalizado: un registro puede tener varios padres. CODASYL Relaciones múltiples sin duplicar registros.
Orientado a objetos Objetos de la aplicación almacenados tal cual, sin descomponerlos en filas. ObjectDB Aplicaciones escritas en lenguajes orientados a objetos.
Documentos Documentos JSON o XML completos, con esquema flexible. MongoDB, CouchDB Contenido variado: catálogos, perfiles, configuraciones.
Clave-valor Pares de clave y valor, sin estructura fija. Redis, DynamoDB Caché, sesiones y datos de lectura muy rápida.
Columnares Guarda los datos por columnas y no por filas. Cassandra, HBase Analítica y agregaciones sobre grandes volúmenes.
Grafos Nodos y aristas que modelan relaciones directamente. Neo4j Redes sociales, rutas y recomendaciones.
Idea clave

No existe un modelo «mejor» en abstracto: el criterio es ajustar la forma de los datos a la forma del problema. Si los datos son entidades con relaciones claras y reglas de negocio estrictas, manda el modelo relacional; si el documento o el grafo ya dibuja la respuesta, conviene un modelo no relacional.

Criterio 3 — Forma de distribuir la información

El tercer criterio pregunta dónde y cómo se reparte la información entre los equipos que la usan:

Forma Características Ejemplos
Centralizada Todo vive en un solo servidor; los accesos se hacen desde ahí. Base de datos de una sola oficina
Cliente-servidor La aplicación corre en el cliente y la base en el servidor, comunicados por red. PostgreSQL, Oracle, SQL Server
Distribuida Los datos están en varios nodos o sedes y el sistema los presenta con transparencia de localización. Bases repartidas por sucursales
Paralela Varios procesadores atienden la consulta a la vez (MPP); enfocada en analítica. Almacenes de datos para reportes
Replicada / nube Copias de los datos en varios sitios para alta disponibilidad y tolerancia a fallos. Despliegues en la nube con varias réplicas

Criterios para elegir

Antes de instalar nada conviene responder cinco preguntas cortas sobre el proyecto:

  1. Número de usuarios simultáneos: ¿trabaja una persona o cien a la vez?
  2. Tipo y estructura de los datos: son homogéneos y relacionados, o variables y documentados.
  3. Ubicación geográfica: ¿todo en una sede o repartido entre varias?
  4. Volumen y tipo de consultas: transacciones cortas (OLTP) frente a análisis de grandes volúmenes.
  5. Presupuesto: licencias, hardware, costos en la nube y equipo humano para administrarlo.

Ideas para llevar

Resumen

1) Clasificar un SGBD responde a la necesidad del proyecto, no a la moda. 2) Los tres criterios son cantidad de usuarios, modelo de datos y forma de distribuir la información. 3) Ninguno es mejor que otro: se combinan para descartar opciones y justificar la elección.

Con estos tres criterios ya podemos ordenar cualquier gestor en una casilla concreta. Pero queda la pregunta más frecuente en los exámenes: ¿el modelo relacional sigue siendo la única opción? Ese es el tema de la siguiente entrada.
